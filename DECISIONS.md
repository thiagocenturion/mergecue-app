# MergeCue — decisions and open questions

Living record of technical decisions (Phase 0 onward). Newest entries at the bottom of each section.

## Environment (inspected 2026-09-27)
- macOS 26.6.2 (arm64, 14 cores), Xcode 26.6 (17F113), Swift 6.3.3, xcodegen installed.
- Agents found: Claude Code 2.1.283 (`~/.local/bin/claude`), Codex CLI 0.153.4 bundled at
  `/Applications/ChatGPT.app/Contents/Resources/codex` (not on PATH).
- `gh` is logged in to github.com; no GitLab (`glab`) or Bitbucket credentials found locally.
- Signing identities: Apple Development + Apple Distribution. **No Developer ID Application** certificate → a
  notarized direct-download build is not possible yet.
- Project directory was empty: new git repository created.

| D17 | Two shared coders (`MergeCueCoding`): **storage** = `.deferredToDate` (exact `timeIntervalSinceReferenceDate`), **wire** = RFC 3339 UTC with milliseconds (fraction omitted when zero). `JSONValue.defaultEncoder/Decoder` = wire. `Set` fields encode as sorted arrays; `MergeCueCoding.digest` for fingerprints. | `.iso8601` dropped sub-second precision (GitLab `updated_at` never matched the stored snapshot); `.secondsSince1970` also loses low bits of wall-clock dates (verified on ~56 % of random dates). Hash-order `Set` encoding changed digests across launches. |
| D18 | `account`/`providerKind`/`number` on `ChangeEvent`, `AttentionItem` and `TaskOrigin` are derived from the `ChangeRequestKey` (`private(set)`, no init overrides). Key equality follows the stable `id` (`ChangeRequestKey` ignores `number`); `StableID` NFC-normalizes components. | Prevents cross-provider/account mixing (plan §11); keeps `Set`/dictionary lookups consistent with primary keys. |
| D19 | `ChangeRequestRef` accepts `_` hosts, IPv6 literals, and any path segment without `/ # !`, whitespace or control characters; encoding an invalid ref throws. Refs are resolved with `matches` (repo path case-insensitive), scoped to the task's account. | Encode/decode symmetry (an unreadable `TaskOrigin` poisons the task row); agents type refs by hand. |
| D20 | Remote URLs are sanitized at the Core boundary (`CanonicalRemote.sanitizedURL`, applied by `GitRemote` and mapping types). | Remotes like `https://user:TOKEN@…` must never reach SQLite, logs or MCP. |
| D21 | `SecretRedactor` rules anchor on look-behinds instead of `\b` and bound key prefixes (≤ 64). Raw logs are **not** pre-trimmed before redaction. | The `\b` + lazy-prefix patterns were quadratic (8 KB of `a-` took 10 s). Pre-trimming could cut a PEM `BEGIN` line and leak the key body; redaction is now linear, so it is not needed. |
| D22 | The engine gates previews/writes with an **account-specific** capability manifest (`ProviderFactory.capabilities(for: Account)`, default = per-kind). | D30 | **Handoff code**: each new task gets an 8-character code (unambiguous alphabet) that appears only in the handoff prompt (`Work on MergeCue task mc_x (handoff code: K7Q2M9XD). …`). `claim_task` requires it (`handoff_code`, case/dash-insensitive, constant-time; missing/wrong → `validation_failed`, recorded as a rejected call). | D35 | **Polling model (GitButler-style), replacing "every account every 90 s".** Lists: per account every 15 min (`listInterval`), immediately at launch, on manual Refresh (never debounced), and on popover open / main window key / wake / network recovery — skipped within 60 s of the previous event refresh or successful list. Details, per change request, by time since it last changed (new activity, head change, check state change): 30 s for the first 10 min, 5 min up to 1 h, 30 min after; CRs with a task waiting for / claimed by an agent (engine → `SyncControlling.setActiveChangeRequests`) or pending checks stay at 30 s; a changed list version always hydrates at once. Per-CR errors back off 30 s → 5 min → 30 min; `not found` / `forbidden` are terminal for that CR until its list version changes, a manual Refresh, or a return/focus at least 15 min after the failure; they are shown per CR (PR list row, account status "1 PR couldn't be loaded: not found", tap to retry) and an account whose CRs all failed is never shown as healthy-empty. Account level: auth expired stops; a rate limit waits for the provider's reset (`Retry-After`, GitHub `x-ratelimit-reset`, GitLab `RateLimit-Reset`), else 5 → 15 → 60 min, shown as "Rate limited — retrying at HH:MM" with the provider and account. Every provider HTTP request is counted per account over a rolling hour (`CountingTransport` in `LiveProviderFactory`; 304s excluded) and shown in Settings ▸ Accounts; above 75 % of a soft budget (GitHub 1500/h, GitLab 1000/h, Bitbucket 500/h) detail intervals double, at the budget they are ×4. Conditional requests: GitLab listings (existing), GitHub REST directory/repository reads, and every Bitbucket GET now send `If-None-Match` after a response carried an ETag (GitHub's sync path is GraphQL, which has no ETags; Bitbucket's CORS policy exposes `ETag`/allows `If-None-Match` — not verified live, harmless if unsupported). | Owner report: Settings ▸ Accounts showed a rate limit resetting "in some hours" — Sync re-hydrated pending/stale CRs and retried CRs that failed with 404 on every 90 s cycle, forever. Modelled on GitButler (PR list every 15 min + refetch on focus; per-PR detail 5 s → 30 s → 5 min → 30 min by time since last change; error backoff; terminal errors stop until refocus). Regression test: 4 CRs answering 404 cost 14 provider calls per idle hour instead of 240 (76 with a popover open every 2 min). Tunables live in `SyncConfiguration`; reversible by configuration. |
| D36 | **Watched repositories, per-account refresh interval, incremental hydration** (owner report: a Bitbucket refresh in a ~500-repository workspace sent ~10 requests in one second for 1-2 interesting repositories). (1) `Account.watchedRepositories: [RepoKey]?` (additive): nil = follow the checkout mappings (all when none; demo accounts: all), empty = all, else only those repositories; mapping a repository adds it to an explicit non-empty list; `WatchedRepositories.effective`. Sync passes them as `ChangeRequestQuery.repositories` + `restrictToRepositories` (additive) and drops CRs of other repositories (no departure hydration for unwatched ones). Bitbucket authored: one `GET /workspaces/{ws}/pullrequests/{uuid}` per workspace of the watched repositories, filtered client-side (per-repository BBQL `author.uuid` only when the token cannot read it); reviewer/involved: one BBQL query per watched repository (previously every stored repository, ~500, per cycle); GitHub: one search with `repo:` qualifiers (split only past 256 characters); GitLab: `/projects/:id/merge_requests?author_id=` / `reviewer_id=` per watched project (conditional). Sync never lists repositories; the unwatched Bitbucket reviewer fallback (30 most recent repositories) is cached per provider for 6 h, like `/user/workspaces`. Sync's own default tracking is now authored only. (2) `Account.refreshInterval` (5 / 15 default / 30 min / 1 h / manual) is the account's list cadence; detail tiers scale with it: hot (agent task) or pending checks 30 s, recent (< 10 min) 5 min × scale, quiet (< 1 h) the interval, idle 30 min × scale (≥ interval); "manual" = launch + Refresh only (no timer, no event refresh, no automatic detail refresh). A manual Refresh re-lists and hydrates only changed / due / failed / pending-checks / hot CRs. Metadata changes apply to the running syncer in place: the provider (identity caches, ETags) lives as long as the account's credential. (3) `ReviewProvider.hydrate(_:previous:)` (additive, default = full): Bitbucket reads the PR object from the same cycle's listing (`fields=+values.participants,+values.reviewers,+values.summary`; falls back to the detail GET when participants are missing; workspace endpoint honouring `fields` is inferred, needs one live check), `/comments` only when `comment_count` > 0 and it / `updated_on` / head changed, `/tasks` only when `task_count` > 0 and changed, commits and diffstat only when source/destination commits changed and from `/commits/{src}?exclude={dst}` and `/diffstat/{src}..{dst}?topic=true` (no 302; forks keep the PR endpoints; same for `diff`), `/statuses` only on a new head, a pending check, or head/check activity < 10 min, Pipelines + steps only when a Pipelines status is not green and differs from the one the cached steps belong to. GitLab: project and source project from the previous snapshot, discussions only when `user_notes_count` / `updated_at` / head changed, approvals + reviewers when `updated_at` / head changed, jobs when the head pipeline id/status changed or a check was pending, commits/diffs/versions when head/base/start changed (versions kept in `nativeRefs`). GitHub: unchanged (one GraphQL query, only when its list version changed or it is due). Bitbucket list versions include `comment_count` / `task_count`. (4) `APIClient` shares identical concurrent GETs and caps requests in flight (`maxConcurrentRequests`: 3 GitHub/GitLab, 2 Bitbucket); `hydrateConcurrency` 4 → 3. (5) Accounting: `URLSessionTransport` reports followed redirects (`x-mergecue-redirect-hops`) and `CountingTransport` counts each hop; Bitbucket 304s count (not documented as free); `BitbucketRateLimitParser` reads `X-RateLimit-Limit` / `X-RateLimit-NearLimit`, and a near-limit answer slows the account down ×4 for 15 min (`ProviderRequestLedger.recordNearLimit`); a rate limit without reset time waits until the account's own last-hour count is under half its budget (at least the 5 min fallback). Writes: Bitbucket request-changes + comment POSTs are 1 s apart; a 202 merge is confirmed by polling before success. Measured (`SyncRequestCountTests`, provider requests incl. redirect hops; before = main 6d6e57e, transport requests): Bitbucket 500 repos / 2 authored PRs first sync / unchanged refresh / one new comment 19 / 2 / 10 → 10 / 1 / 2 (2 watched); with review requests 520 / 502 / 510 → 12 / 3 / 4 (2 watched), 42 / 31 / 32 (nothing watched); GitHub fixtures 5 / 1 / 4 → 5 / 1 / 4; GitLab fixtures 23 / 2 / 12 → 22 / 2 / 9 (21 / 2 / 9 watching one project). Not done: one combined `author OR reviewers` BBQL query per repository (saves one request per cycle with review requests on; unverified live and Sync lists scopes separately); restrictive `fields=` lists (payload only, risk of dropping mapped fields); Bearer for API tokens. | Reversible: clear the watched list (all repositories) and pick 5 min to get close to D35's cadence. Live Bitbucket behaviour of `fields` on the workspace listing, `/commits/{src}?exclude=` and `/diffstat/{spec}?topic=true` is from the 2026 OpenAPI spec, not verified against the owner's workspace yet. |
